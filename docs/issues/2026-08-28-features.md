# Versioned feature transformations and pipeline replacement

Date: 2026-08-28. Status: `proposed`. Scope: transformation configuration,
compilation, Rust/Python parity, and replacement of the retained legacy
pipeline.

## Context

The feature extractor refactor and deterministic historical trade replay are
complete. `FeatureVectorSpec` is now the versioned configuration and
serialization boundary for raw feature extraction, while
`FeatureExtractor<F, V>` is the allocation-free event-processing runtime.

Transformation support has not crossed that refactor:

- `features/pipeline/mod.rs` still depends on the removed
  `IndicatorFeatures` and `IndicatorFeatureVector` interfaces and is excluded
  from `features/mod.rs`;
- `StandardScaler` and `ParallelTransformer` are Rust-only runtime types;
- transformation configuration is not represented in a versioned artifact;
- Python cannot construct or execute the same transformation path as Rust;
- final model-input IDs, width, and ordering are not defined independently of
  the raw feature-vector layout.

Mechanically adapting the old `Pipeline` would make it compile, but would not
resolve these interface and parity problems.

## Recommendation

Treat fitted transformations as part of the persisted, versioned model-input
artifact. Keep `FeatureVectorSpec` focused on raw feature extraction and add a
separate `ModelInputSpec` that owns:

1. one `FeatureVectorSpec`;
2. ordered transformation definitions;
3. the final model-input IDs and width;
4. optional version/checksum metadata needed to validate a saved model
   artifact.

The new spec should compile into a runtime module that owns a
`FeatureExtractor` and the compiled transformation state. Its external seam
should remain small:

```rust,ignore
pipeline.handle_event(event)?;
pipeline.raw_values();
pipeline.values();
pipeline.output_ids();
```

The names are illustrative, not an agreed interface. The important properties
are that callers dispatch an event once, raw extractor values remain available
for diagnostics, and `values()` exposes the exact ordered vector passed to the
model.

This should replace the retained legacy pipeline rather than be layered on top
of it. Deleting the new module should cause transformation compilation,
validation, execution, output layout, and parity behavior to reappear in every
caller; that depth is what justifies the module.

## Initial transformation scope

Support only a per-feature standard scaler initially. Each transformed output
needs its own fitted parameters:

```text
output = (input - mean) / scale
```

A definition should identify its input by stable `FeatureId`, not by a raw
numeric index. Compilation resolves IDs to indexes once, validates the complete
layout, and stores only indexes and numeric parameters on the hot path.

The existing `StandardScaler` applies one mean and deviation to every selected
input. That shape is insufficient for a fitted scaler where each feature
normally has different statistics. It should be replaced or redesigned instead
of serialized as-is.

The first implementation should apply transformations in one compiled parallel
stage against the raw feature vector. Arbitrary transformer chains or a general
graph should wait until a concrete transformation requires them. This keeps
ordering and `NaN` behavior easy to define and avoids creating a shallow graph
interface prematurely.

## Decisions required before implementation

### 1. Artifact ownership

Recommended: transformations are stored with the versioned model-input
artifact. Saving only feature extraction while configuring preprocessing
separately makes train/serve skew possible.

### 2. Output contents

Recommended: the model-input vector contains only declared final outputs. Raw
feature values remain available through a separate accessor and are not
implicitly copied into the final vector. A caller that wants a raw value in the
model input should declare an explicit identity/pass-through output.

### 3. Transformation ordering

Recommended for the first version: every transformation reads from the raw
feature vector and writes to a statically assigned output span. Do not support
chaining until there is a real use case that cannot be expressed this way.

### 4. Missing values

Recommended: preserve `NaN`. A standard scaler receiving `NaN` writes `NaN`.
It must not replace unavailable warm-up values with zero or retain an older
transformed value.

### 5. Invalid fitted parameters

Recommended: compilation rejects non-finite means, non-finite scales, and zero
or negative scales. Validation should identify the transformation definition
and output ID that failed.

### 6. Numeric representation

The serialized artifact needs one cross-language representation for fitted
parameters while runtimes may use `f32` or `f64` output storage. Decide whether
the artifact stores JSON numbers as `f64` and compilation converts them to `F`,
or whether transformation execution is intentionally fixed to `f64`. The
current `Float` trait has no conversion from `f64`, so generic conversion would
require a small trait change.

### 7. IDs and collisions

Recommended: every final output has an explicit stable ID. Compilation rejects
duplicate output IDs and references to unknown raw `FeatureId` values. Decide
whether raw and final IDs may share a name; allowing it is convenient for
identity outputs but must remain unambiguous because they belong to different
layouts.

### 8. Serialization versioning

Recommended: `ModelInputSpec` has its own version instead of reusing the
`FeatureVectorSpec` version. Strictly reject unknown fields and unsupported
versions, and serialize in one canonical order so Rust and Python produce
identical artifacts.

## Proposed implementation sequence

### Phase 1: record the contract

- Add an ADR for the decisions above.
- Specify canonical JSON with one raw feature spec and one standard-scaler
  transformation group.
- Include examples for identity outputs, scaled outputs, warm-up `NaN`, and
  validation failures.

No pipeline code should be refactored until this contract is agreed.

### Phase 2: core definitions and compiler

- Add documented `ModelInputSpec` and transformation-definition types.
- Resolve input IDs and assign final output indexes during compilation.
- Validate dimensions, IDs, parameters, and storage capacity before runtime
  state is created.
- Compile standard scaling into contiguous arrays or boxed slices suitable for
  allocation-free updates.
- Add serialization round-trip and rejection tests behind the existing `serde`
  feature.

### Phase 3: runtime replacement

- Add the new runtime module around `FeatureExtractor` and the compiled
  transformation stage.
- Initialize final output cells to `NaN`.
- Transform after every accepted event and do not transform after a rejected
  event.
- Expose raw values, final values, and final output IDs through the external
  seam.
- Delete the stale legacy pipeline once equivalent required behavior is
  covered.

### Phase 4: Python parity

- Expose the same model-input spec and canonical JSON through Python.
- Run batch historical data and event-by-event Rust data through the same
  compiled semantics.
- Preserve configured output dtype without changing fitted-parameter meaning.
- Add cross-language fixtures asserting identical IDs, ordering, `NaN`
  positions, and numeric results.

### Phase 5: end-to-end verification

- Extend the deterministic historical trade replay with an optional
  model-input spec or add a second focused example.
- Verify that the saved artifact produces identical final model vectors in
  Rust and Python.
- Run formatting, all workspace targets and features, Python tests, the
  maintained notebook, and strict Clippy.

## Performance constraints

- Allocation is allowed while parsing and compiling a spec.
- `handle_event` and transformation execution must not allocate.
- Input IDs must resolve to numeric indexes during compilation, never during
  event handling.
- Runtime loops should use precompiled contiguous storage and avoid trait-object
  dispatch unless measurements justify it.
- The final vector must be written directly; do not construct temporary vectors
  per event.

## Acceptance criteria

- One canonical artifact fully describes raw extraction and final model-input
  transformation.
- Rust and Python serialize and deserialize that artifact identically.
- Standard scaling uses per-feature fitted parameters.
- Unknown input IDs, duplicate output IDs, invalid dimensions, and invalid
  fitted parameters fail before the first event is processed.
- Warm-up and missing values remain `NaN` in the final vector.
- Rejected events leave raw and transformed state unchanged.
- Final output IDs and ordering are stable and tested.
- Event handling and transformation execution perform no heap allocation.
- The old pipeline and its references to removed interfaces are deleted.
- Workspace tests, Python tests, the notebook, examples, formatting, and strict
  Clippy pass.

## Non-goals

- Loading exchange-specific historical data.
- Label generation or model training.
- A general transformation graph or arbitrary user-defined transformations.
- Persisting trained ML model binaries inside `fiml`.
- Order-book feature derivations; those should remain a separate design task.

## Work after transformations

The next independent design task should be order-book derivations. It must
define ownership and synchronization of order-book state, feature routing, and
conversion from `Decimal` book values to the extractor's `Float` output type.
