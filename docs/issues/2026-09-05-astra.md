# Codebase review — 2026-09-05

Review of the current Rust core and Python bindings, focused on correctness,
runtime allocation, and feature-vector parity. Seven issues were reproduced.
No implementation changes were made as part of this review.

## 1. P1 — Non-finite input permanently poisons indicators — resolved

**Location:** [FeatureExtractor::handle_event](../../crates/fiml/src/features/feature_extractor.rs)
and the shared Python runtime's `build_event` / `require` functions in
[lib.rs](../../crates/fiml-python/src/lib.rs).

Rust event dispatch and Python `update` / `transform` previously accepted NaN and infinity
without validating numeric payloads. Incremental indicator state becomes
non-finite and does not recover when the offending sample leaves the window.
The DataFrame `compute_features` path already validates finiteness, so the
ingestion paths have different behavior.

**Original reproduction:** Send prices `100, NaN, 102, 103, 104` through a 2-period SMA
with increasing timestamps. Every event succeeds, but the final value remains
NaN instead of the mean of the last two valid prices, `103.5`. This was reproduced
through both the Rust extractor and Python low-level updates.

**Impact:** One malformed tick silently disables an indicator for the remaining
runtime lifetime. Its NaN output is indistinguishable from warm-up or missing
data.

**Resolution (2026-09-05):** `Event::validate_finite_values` now rejects NaN and
±infinity with the allocation-free typed error
`InvalidArgumentError::NonFiniteEventValue { field: EventField }`. Standalone
price/volume and both trade fields are checked, with trade price checked first.
The extractor validates after timestamp ordering and before any mutation,
including for unsubscribed symbols. Pipelines inherit this rejection.
Python's shared `build_event` applies the same validation before batch dispatch,
preserving `ValueError` and `row N:` context.

Rejected inputs leave feature values, raw/final snapshots, timed state, and the
timestamp watermark unchanged. A rejected first Python input does not lock
output dtype. Finite zero/negative low-level inputs remain accepted, unused
payload columns remain ignored, and DataFrame validation still requires positive
values. Direct standalone indicator callers must supply finite inputs; recovery
from already-poisoned state and arithmetic overflow from finite inputs remain
outside this fix.

**Verification:** Regression tests cover all four numeric fields with NaN and
both infinities, unchanged state for subscribed/unsubscribed symbols, atomic
Python batches, dtype locking, and replay parity with a fresh runtime. The
2-period SMA now ends at `103.5` after rejecting NaN and accepting `102, 103, 104`.
The extended allocation counter confirms accepted and rejected numeric events
allocate nothing without formatting errors in the measured section.

- `cargo test --workspace --all-targets --all-features` — passed
- `cargo test --workspace --all-features --doc` — passed
- Python suite with rebuilt bindings — **178 passed**
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` — passed
- `cargo fmt --all -- --check` — passed

This resolves the event-ingestion issue also recorded in section 1.4 of the
[July review](2026-07-25-claude-review.md).

## 2. P1 — Exceeding the symbol limit poisons the global interner — resolved

**Location:** `SymbolInterner::intern`, `symbols::intern`, and `symbols::resolve`
in [symbols.rs](../../crates/fiml/src/symbols.rs).

The process-wide interner permits 512 total symbols, including GLOBAL. Previously,
adding another distinct market symbol executed an assertion while holding the
global mutex. Unwinding poisoned the mutex, and subsequent operations called
`lock().unwrap()`.

**Original reproduction:** In an isolated process, intern 511 distinct market symbols,
then attempt a 512th. Catch the panic and attempt to intern an existing name or
resolve an existing symbol. Both subsequent operations also panic.

**Impact:** The limit accumulates across extractors and configuration loads in
one process. A single capacity failure breaks later symbol lookups and
resolution, including operations on previously valid symbols.

**Resolution (2026-09-06):** The shared interner now checks capacity before
inserting a new name and returns the existing typed `LimitExceeded` error with
`LimitTarget::Symbols`. Existing names are looked up first, so ASCII case
variants and GLOBAL still work at capacity. Repeated capacity errors leave
the interner and its mutex usable.

`Symbol::new` and `symbols::intern` now return `fiml::Result<Symbol>`; string
`From` implementations were replaced with `TryFrom`. Rust callers must handle
or propagate the result (for example, `Symbol::new(name)?`). Examples and tests
were migrated. Symbol and feature-spec deserialization propagate the error,
as do Python builders and runtime symbol registration, which raise `ValueError`
without changing the affected spec, runtime handles, or feature state.
The process-wide capacity remains 512, including GLOBAL; dropping runtimes
does not reclaim interned names.

**Verification:** An isolated Rust integration test fills the interner and
checks all public string-construction paths, deserialization, repeated failures,
existing-name lookup/resolution/formatting, and continued event processing.
A Python subprocess test covers all six symbol-based builders, both runtime
types, and raw/model spec and runtime JSON loaders, including successful reuse
after rejection.

- `cargo test --workspace --all-targets --all-features -q` — passed
- `cargo test -p fiml --no-default-features --test symbol_capacity -q` — passed
- Python suite with rebuilt bindings — **179 passed**
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` — passed
- `cargo fmt --all -- --check` — passed

## 3. P1 — Extractor construction paths disagree about missing values

**Location:** `FeatureExtractorBuilder::build` in
[feature_extractor_builder.rs](../../crates/fiml/src/features/feature_extractor_builder.rs),
compared with `FeatureVectorSpec::build` in
[feature_vector_spec.rs](../../crates/fiml/src/features/serde/feature_vector_spec.rs).

The direct builder preserves the supplied output vector's initial contents.
The built-in vector constructors initialize cells to zero. Spec construction
instead resets every cell to NaN, including reserved cells.

**Reproduction:** Construct identical 2-period, full-window price SMAs through
the direct builder and through a feature-vector spec. Dispatch a time event
before any matching price event. The direct builder exposes `[0.0]`; the spec
path exposes `[NaN]`.

**Impact:** Identical feature definitions produce different missing-value
snapshots depending on construction path. Rust callers using the direct builder
can disagree with Python callers using specs, violating the warm-up contract.
Caller-supplied stale values can also remain visible until a feature writes.

**Suggested fix:** Initialize all output storage consistently to NaN during
extractor construction, covering active and reserved cells.

## 4. P2 — Valid sliced DataFrames fail the contiguous-array requirement

**Location:** `_compute_features` in
[__init__.py](../../crates/fiml-python/python/fiml/__init__.py) and
`RuntimeDriver::transform` in [lib.rs](../../crates/fiml-python/src/lib.rs).

The DataFrame wrapper obtains timestamps with
`to_numpy(dtype=np.int64, copy=False)`. This can retain a strided view. Numeric
payload arrays can also retain non-contiguous storage, while the Rust binding
requires contiguous arrays through `as_slice()`.

**Reproduction:** Create a valid, chronologically ordered six-row trade
DataFrame. `compute_features(df)` succeeds, but
`compute_features(df.iloc[::2])` raises:

```text
TypeError: The given array is not contiguous
```

The sliced timestamp array had a stride of 16 bytes rather than 8.

**Impact:** Ordinary pandas slicing produces valid inputs that unexpectedly
fail during replay. The shared wrapper affects both feature extractors and
model-input pipelines.

**Suggested fix:** Normalize arrays passed from the DataFrame wrapper with
`np.ascontiguousarray`, which copies only when necessary.

## 5. P2 — Timed SMA accepts late windows without initializing their history

**Location:** `SimpleMovingAverageTimed::add_window_with_periods` in
[indicator.rs](../../crates/fiml/src/indicators/averages/sma/indicator.rs).

Unlike sample SMA and timed OBV, timed SMA does not reject adding a window after
data has arrived. The new window starts with an empty sum and bucket count even
though the shared ring already contains relevant history.

**Reproduction:** With 1-second aggregation and `FirstValue` warm-up:

1. Add a 2-period window.
2. Update with value `100` at timestamp `0`.
3. Add another 2-period window; this succeeds.
4. Update with value `200` at timestamp `1000`.

The original window returns `150`; the newly added identical window returns
`200`.

**Impact:** A successful public API call creates a window whose value omits
available history and disagrees with an identically configured existing window.

**Suggested fix:** Reject window additions after ingestion using the existing
`WindowAddedAfterData` error, consistent with the other window indicators.

## 6. P2 — Order-book dispatch allocates on the event-processing path

**Location:** `BookSide::update_level` in
[book_side.rs](../../crates/fiml/src/order_book/book_side.rs).

Order-book levels live in a `BTreeMap`. Inserting new levels can allocate nodes
inside an accepted `FeatureExtractor::handle_event` call. Snapshot replacement
also clears and rebuilds these maps. This does not satisfy the documented
allocation-free runtime boundary.

**Reproduction:** Configure an order book, apply an empty snapshot, and construct
a delta containing one new bid level before enabling an allocation counter.
Dispatching that already-constructed delta performed one heap allocation inside
`handle_event`.

**Impact:** Order-book ingestion can incur allocator work despite the extractor's
allocation-free guarantee. The existing pipeline allocation checks do not cover
this path.

**Suggested fix:** If the guarantee includes order books, use bounded,
preallocated level storage and add allocation coverage for order-book updates.
Otherwise explicitly narrow the documented guarantee to the supported paths.

## 7. P3 — Extreme timestamps overflow timed-indicator arithmetic

**Location:** `bucket_start` and bucket-expiration arithmetic in timed
[SMA](../../crates/fiml/src/indicators/averages/sma/indicator.rs),
[OBV](../../crates/fiml/src/indicators/volume/obv/indicator.rs), and
[trade count](../../crates/fiml/src/indicators/counts/trade_count.rs).

Bucket-start calculation subtracts a nonnegative remainder directly from an
`i64` timestamp. Near `i64::MIN`, the mathematical bucket start can fall outside
the representable range. Expiration checks also add window durations directly
to bucket timestamps, allowing overflow near the upper boundary.

**Reproduction:** Update a timed SMA configured with 1-second aggregation at
timestamp `i64::MIN`. The debug build panics in bucket-start arithmetic.

**Impact:** Extreme but representable input timestamps can cause a panic;
unchecked overflow can instead wrap when overflow checks are disabled. This is
a boundary-input issue rather than a normal market-timestamp case.

**Suggested fix:** Define and validate supported timestamp bounds before state
mutation, or use wider intermediate arithmetic for bucket alignment and expiry.
