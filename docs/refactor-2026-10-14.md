# Refactoring and implementation order — 2026-10-14

Status: planned. This document records the agreed order for the next-version
features and the six simplifications identified in the codebase review.
Creating these tickets does not mean their changes are implemented.

## Decision

Fix the UTC-offset parsing bug and simplify scalar transformer definitions before
adding the remaining features. Complete #165–#167 before revisiting the four
other refactors. Preserve the shared feature compiler, static runtime dispatch,
preallocated histories, and common Python replay driver.

Keep each refactor separate from new numerical behavior. The purpose of the
preparatory work is to remove duplication that the next feature would otherwise
expand; the other cleanup does not block feature implementation.

## Current baseline

- Reviewed local commit: `afdcbae` (`feat(transform): trajectory transform`).
- [#164: trajectory-shape transformers](https://github.com/pbezglasny/fiml/issues/164)
  is still open on GitHub, but the local commit contains its calculations,
  Python builders, serialization, shared fixtures, documentation, benchmarks,
  and allocation coverage. Verify the acceptance criteria and integration status
  before treating it as completed; do not reimplement it from scratch.
- The preceding review passed 315 Rust unit/integration tests and 2 doctests
  using `cargo test -p fiml --all-features --offline`. It did not run the Python
  suite, notebooks, or benchmarks. This planning change does not rerun them.
- The UTC-offset issue was reproduced through actual JSON deserialization:
  malformed signed components are accepted and an extreme negative component
  panics in a debug build.

## Dependencies and limits

- [#172](https://github.com/pbezglasny/fiml/issues/172) is an independent correctness fix. Its placement first
  does not imply that the new features require the offset parser.
- [#173](https://github.com/pbezglasny/fiml/issues/173) is the agreed preparatory refactor for
  #165. Complete its caller migration in a separate behavior-preserving change.
- #165 and #166 are independent. Their order above is a preference, not a
  technical dependency.
- #166 needs old-to-new size transitions. Deriving flow solely from the final
  visible book loses information. Applied, buffered, stale, rejected, and
  replayed updates need explicit semantics. Check the actual ingestion support
  associated with [#112](https://github.com/pbezglasny/fiml/issues/112), whose
  issue status may lag the local implementation.
- #167 has multiple output coordinates. Keep it a stage with the small scope
  requested by its issue. Assess reuse of the existing `History`/`Merge`
  implementation after defining segment composition and normalization; do not
  introduce an arbitrary-dimensional framework in advance.
- Review [#176](https://github.com/pbezglasny/fiml/issues/176) alongside the direction of
  [#150](https://github.com/pbezglasny/fiml/issues/150) before changing every
  raw-feature caller.
- Keep [#177](https://github.com/pbezglasny/fiml/issues/177) separate from #166 so storage-order
  regressions can be distinguished from flow-accounting errors.

## Verification for implementation

Use each issue's acceptance criteria and the existing CI checks. Changes to
representations must preserve fixture output order, NaN positions, observation
masks, clocks, warmup behavior, and Rust/Python parity.

- Run `cargo fmt --all` after Rust edits and verify formatting.
- Run the Rust tests and strict workspace Clippy checks used by CI.
- Run Python tests and maintained notebook checks for binding, artifact, or
  public-interface changes; keep the full CI checks enabled.
- Preserve steady-state allocation tests. Add focused behavioral cases where
  the new features or the UTC parser bug require them.
- Keep schema and canonical serialization coverage for public spec changes.
- Run relevant existing benchmarks for window-storage or book-query changes;
  record measurement gaps. #167 explicitly requires Criterion coverage.
- Update affected callers, fixtures, examples, exports, builder paths, migration
  notes, and public documentation in the same change.

Implementation details and acceptance criteria live in the linked GitHub issues.
Update this ordering record if those requirements or dependencies change.
