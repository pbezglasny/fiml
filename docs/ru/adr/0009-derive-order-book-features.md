# ADR 0009: Вычисление признаков стакана

Статус: принято

Дата: 2026-09-08

<a id="context"></a>

## Контекст

`FeatureExtractor` уже владеет настроенными стаканами и маршрутизирует видимые
обновления через `FeatureRoute::OrderBook`. Приватный обработчик
`FeatureDerivation::update_order_book` ещё не реализован. `OrderBook` уже считает
индикаторы, нужные для первой интеграции.

Признаки стакана должны писать в тот же вектор со стабильными ID без дополнительных
выделений при вычислении. Rust принимает стаканы через `add_order_book`, но JSON/
спецификация и Python пока не настраивают это состояние.

<a id="decision"></a>

## Решение

Добавить шесть публичных `FeatureKey`: `OrderBookMidPrice`, `OrderBookSpread`,
`OrderBookSpreadBps`, `OrderBookWeightedMidPrice`, `OrderBookMicroprice`,
`OrderBookImbalance`. Каждый принимает `symbol`, дисбаланс также `n_levels: usize`.
Источник события и политика прогрева не нужны.

Генерировать ID по существующему кодированию символа, `source=order_book` и глубине
дисбаланса. Сохранять пользовательские ID. Добавить метки ошибок и компилятор.
При создании отклонять нулевую глубину, повторные ключи/ID и отсутствующие стаканы;
последние возвращают `OrderBookNotConfigured`.

Объединять дисбалансы одного символа в одно вычисление с прежним относительным
порядком и правилами группировки. Лимит — 16 выходов. Глубины хранить в фиксированном
хранилище, вычислять каждую через `OrderBook::imbalance`, без нового общего алгоритма.

Адаптеры разместить в одном приватном модуле и подключить к маршруту/обработчику
стакана. Использовать шесть существующих расчётов без изменения формул.
Преобразовать `Decimal` через `ToPrimitive::to_f64` установленной зависимости и
писать в назначенный диапазон. Отсутствие результата/ошибка конверсии даёт `NaN`.

Все выходы начинаются с `NaN`, даже с заполненным стаканом. Обновлять после
применённого изменения или синхронизации по конечному видимому состоянию.
Буферизованные, игнорируемые, отклонённые и посторонние события выход не меняют.
В частности, отклонённый разрыв последовательности не очищает прежние значения.
Группа дисбалансов считается одним обновлённым признаком.

Первая реализация поддерживает Rust-построитель. JSON, конфигурация стакана
спецификацией и Python отложены. Расширить полный разбор ключей и каноническую
сортировку для сохранения существующих функций. Сериализация новых ключей даёт
явную ошибку неподдерживаемого признака; создание по спецификации без нужных
стаканов — ошибку отсутствующего стакана.

<a id="consequences"></a>

## Последствия

- Значения стакана становятся обычными именованными выходами через Rust-построитель
  и закрытую диспетчеризацию.
- Вычисление не добавляет выделений или зависимостей. Хранилище стакана сохраняет
  прежние выделения; не все его изменения становятся безаллокативными.
- Групповой дисбаланс повторяет обход на глубину. Общий обход возможен, если
  измерения покажут значимость затрат.
- Формулы, доступная глубина и синхронизация остаются определяющими. Лучшие
  котировки, запросы глубины, сглаживание и новые индикаторы не добавляются.
- Примеры Rust показывают настройку, определения и снимки/дельты. Новые типы и
  модуль требуют документации назначения.
- В отличие от полной интеграции ADR 0007, JSON/Python намеренно отложены.
  Существующие сериализованные признаки сохраняют поведение.

<a id="validation"></a>

## Проверка

- Проверить шесть выходов по известным значениям, различая взвешенную среднюю и
  микропрайс, пустые/односторонние стаканы и глубину больше доступной.
- Проверить порядок глубин, лимит 16, маршрутизацию символов, дубли, нулевую
  глубину, отсутствие стакана, стабильные стандартные и пользовательские ID.
- Проверить снимки/дельты, буферизацию, старые обновления, разрывы и синхронизацию
  с реальными подписчиками; начальные NaN и неизменность на посторонних событиях.
- Проверить сериализацию новых ключей и регрессии спецификации по дополнению ниже.
- Использовать счётчик выделений с готовыми обновлениями существующих уровней,
  подтвердив отсутствие дополнительных выделений вычисления.
- При реализации выполнить форматирование, все возможности workspace-тестов,
  строгий Clippy и существующие проверки CI Python/блокнотов.

<a id="follow-up-serialize-feature-definitions"></a>

## Продолжение: сериализация определений

2026-09-08 добавлена поддержка JSON для `docs/example_of_store_definition.json`.
Это отменяет отсрочку сериализации. Настройка стакана и ввод событий Python пока
отложены; загруженные определения Rust передаются построителю с `add_order_book`.
Создание по спецификации всё ещё отклоняет недостающие стаканы.

Формат `1.0` получает шесть snake-case видов от `order_book_mid_price` до
`order_book_imbalance`. Источник строго `{"type": "order_book"}`, символ неглобальный.
Политики прогрева и параметров расчёта нет. Скаляр имеет один выход с необязательным
ID; стандартные скалярные выходы можно опускать. Дисбаланс требует 1–16 выходов
с положительным целым `n_levels` и необязательным ID. Порядок глубин сохраняется.
`window`, параметры событий/полей и `n_levels` других индикаторов запрещены.
Состояние стакана и политика обновления не сериализуются.

Запись и чтение поддерживают определения. JSON-схема, канонический пример и тесты
Rust/Python покрывают расширение; прежние представления и ID не меняются.

<a id="follow-up-remaining-quote-and-depth-queries"></a>

## Продолжение: остальные запросы котировок и глубины

Остальные запросы `OrderBook` открыты как скалярные `FeatureKey` через прежние
построитель, компилятор, маршрут и JSON:

| Суффикс ключа после `OrderBook` | Параметры кроме `symbol` | Выход |
| --- | --- | --- |
| `BestBidPrice`, `BestBidSize`, `BestAskPrice`, `BestAskSize` | Нет | Цена или объём лучшей котировки |
| `LevelSize` | `side`, `price` | Объём на точной цене |
| `NthPrice`, `NthSize` | `side`, `n_levels` | Цена/объём на глубине с отсчётом от 1 |
| `DepthUntilPrice` | `side`, `price` | Накопленный объём до включительного порога |
| `DepthUntilSizePriceFrom` | `side`, `size` | Первая цена для достижения объёма |
| `DepthUntilSizePriceTo` | `side`, `size` | Последняя цена для достижения объёма |
| `DepthUntilSizeTotalSize` | `side`, `size` | Сумма полных уровней, достигающая объёма |
| `VolumeBetweenPrices` | `side`, `from_price`, `to_price` | Объём в `[from_price, to_price)` с любой стороны |

Все запросы используют текущие методы. Три выхода целевого объёма дают `NaN`,
если глубины не хватает; последний уровень учитывается целиком, сумма может
превышать цель. Отсутствующие котировки/уровни дают `NaN`. Накопленная глубина и
интервальный объём дают ноль, если уровней нет. Глубины/целевые объёмы положительны,
цены неотрицательны, границы возрастают; проверка до событий. `top_n` выражается
отдельными скалярными глубинами цены/объёма, а не выходом переменной ширины.

Запросы компилируются независимо, параметры входят в идентичность. Начальные
значения, маршрутизация, буферизация, отклонение и синхронизация прежние.
Вычисление не выделяет память. Перекрывающиеся запросы повторяют обходы; объединять
их следует только по результатам профилирования. Порядок/ID дисбаланса прежние.

Виды JSON — snake-case имена ключей. Лучшие котировки используют скалярный формат.
Параметризованные запросы требуют `options`, например:

```json
{
  "kind": "order_book_depth_until_size_price_to",
  "source": {"type": "order_book"},
  "options": {"side": "bid", "size": "4"},
  "outputs": [{"id": "bid_price_for_four_units"}]
}
```

`side` — `bid`/`ask`; цены и объёмы — точные десятичные строки без округления.
Сериализация и стандартные ID нормализуют масштаб десятичных чисел.
`n_levels` — положительное целое в options (у дисбаланса остаётся в каждом выходе).
У запроса один необязательный ID, нет прогрева. Канонический порядок определяется
видом и стандартным ID с параметрами; пользовательский ID не влияет.
Схема проверяет форму, Rust также представимость Decimal и возрастание границ.

`cargo run -p fiml --example feature_extractor` показывает лучшую котировку и
запрос целевого объёма. Python может записывать/читать определения; настройка
стакана и реальный ввод Python отслеживаются в #112.

## Продолжение: настроенное воспроизведение Rust/Python (2026-09-09)

`FeatureExtractorSpec` владеет необязательным списком `order_books` по символам.
Запись содержит явные `symbol`, `update_policy` (`monotonic`/`contiguous`),
`buffer_size`. Rust предоставляет `OrderBookConfig` и
`FeatureExtractorSpec::with_order_books`, Python —
`FeatureExtractorSpec.configure_order_book`. Сортировка каноническая по символу.
Дубли и глобальный символ запрещены. Недостающие стаканы отклоняются при сборке
экстрактора/конвейера. Старые артефакты `1.0` без списка сохраняют поведение.
Уровни, история, ID последовательности и синхронизация не сериализуются.
Каждое создание начинает с нового стакана и NaN. Нулевая ёмкость сохраняет
поведение ядра, включая ошибки при необходимом сохранении дельты.

Python предоставляет построители и неизменяемые `OrderBookEvent.snapshot`/`.delta`.
Событие содержит имя символа, знаковую миллисекундную метку, uint64 ID и кортежи
уровней. Снимок — пары `(price, size)`, дельта — тройки `(side, price, size)` со
стороной `bid`/`ask`. Цены/объёмы — точные неотрицательные десятичные строки; float
и превышение точности Decimal запрещены без округления. Нулевой объём удаляет.
`update_order_book(event)` и `transform_order_book(events)` используют общую
диспетчеризацию Rust для экстракторов и конвейеров. Старый числовой
`KIND_ORDERBOOK` теперь явно сообщает о миграции вместо отбрасывания котировок.

Конструкторы проверяют данные до выдачи события. Перед пакетом
`transform_order_book` проверяет настроенный символ и порядок времени относительно
рабочей границы и предыдущих строк. Ошибка оставляет весь пакет неприменённым.
Зависимые от состояния ошибки последовательны: предыдущие строки применены,
отклонённая выполняет точный переход синхронизации ядра (включая сохранение дельты
разрыва), позднейшие не применяются. Ошибка указывает индекс строки от нуля;
можно прочитать значения и синхронизировать снимком. Отклонённая строка сохраняет
исходные/итоговые значения и время. Числовая/торговая предпроверка прежняя.
Создание данных и выходного пакета выделяет память на границе Python; вычисление
и преобразования — нет, а хранилище стакана сохраняет прежнее поведение.

<a id="follow-up-configured-dense-storage-2026-09-21"></a>

## Продолжение: настройка плотного хранилища (2026-09-21)

Запись `order_books` может включать
`"dense": {"tick_size": "0.01", "min_price": "90", "max_price": "110"}`.
Точные десятичные строки задают заранее выделенную включительную сетку тиков.
Rust использует
`OrderBookConfig::new(symbol, policy, buffer_size).with_dense(tick_size, min_price, max_price)`.
Тот же JSON работает в Rust/Python, включая конвейеры. Без `dense` сохраняются
BTreeMap и прежний формат. Корректность сетки проверяется при настройке/загрузке;
память выделяется при создании экземпляра. Обновления вне сетки/диапазона отклоняются
до изменения. Плотное хранилище не выделяет память при вставке, удалении и замене
снимка; BTreeMap может выделять при вставке новых уровней.
