# Версионированные преобразования признаков и замена конвейера

Дата: 2026-08-28. Статус: `proposed`. Область: конфигурация/компиляция преобразований,
совпадение Rust/Python, замена сохранённого старого конвейера.

<a id="context"></a>

## Контекст

Рефакторинг экстрактора и детерминированное воспроизведение сделок завершены.
`FeatureExtractorSpec` — граница версии/сериализации исходного извлечения,
`FeatureExtractor<F, V>` — исполнение событий без выделений.

Преобразования ещё не перенесены:

- `features/pipeline/mod.rs` зависит от удалённых `IndicatorFeatures`/
  `IndicatorFeatureVector` и исключён из `features/mod.rs`;
- `StandardScaler`, `ParallelTransformer` — только Rust;
- конфигурации нет в версионированном артефакте;
- Python не может создать/исполнить тот же путь;
- конечные ID, ширина, порядок не определены отдельно от исходной раскладки.

Механическая адаптация старого `Pipeline` даст сборку, но не решит API и совпадение.

<a id="recommendation"></a>

## Рекомендация

Хранить обученные преобразования в версионированном артефакте входа модели.
`FeatureExtractorSpec` оставить исходному извлечению, отдельный `PipelineSpec` владеет:

1. Одним `FeatureExtractorSpec`.
2. Упорядоченными определениями преобразований.
3. Конечными ID и шириной.
4. Необязательными версией/checksum для проверки артефакта модели.

Спецификация компилируется в модуль, владеющий экстрактором и преобразованиями.
Внешняя граница небольшая:

```rust,ignore
pipeline.handle_event(event)?;
pipeline.raw_values();
pipeline.values();
pipeline.output_ids();
```

Имена иллюстративны, не согласованы. Важно: одно событие подаётся один раз,
исходные значения доступны диагностике, `values()` — точный упорядоченный вход модели.

Модуль заменяет старый конвейер, не надстраивается. Его удаление должно возвращать
компиляцию, проверку, исполнение, раскладку и совпадение в каждый вызывающий код;
такая глубина оправдывает модуль.

<a id="initial-transformation-scope"></a>

## Начальный набор преобразований

Сначала только стандартное масштабирование по признаку. Выходу нужны свои параметры:

```text
output = (input - mean) / scale
```

Вход определяется стабильным `FeatureId`, не индексом. Компиляция один раз
разрешает ID, проверяет раскладку, оставляет индексы/числа в горячем пути.

Существующий `StandardScaler` применяет одно среднее/отклонение ко всем входам.
Для обученного scaler с разной статистикой признаков этого мало. Заменить/
перепроектировать, а не сериализовать как есть.

Сначала один скомпилированный параллельный этап над исходным вектором.
Произвольные цепи/граф отложить до конкретной нужды. Так проще порядок и NaN,
без преждевременного поверхностного графового API.

<a id="decisions-required-before-implementation"></a>

## Решения до реализации

<a id="1-artifact-ownership"></a>

### 1. Владение артефактом

Рекомендация: преобразования хранятся вместе с версионированным входом модели.
Раздельные извлечение/предобработка допускают расхождение обучения/применения.

<a id="2-output-contents"></a>

### 2. Содержимое выхода

Только объявленные итоговые выходы. Исходные значения доступны отдельно и не
копируются неявно. Для исходного входа модели объявляется явное тождественное преобразование.

<a id="3-transformation-ordering"></a>

### 3. Порядок преобразований

Сначала все читают исходный вектор и пишут в назначенные диапазоны.
Цепи не поддерживать до реального невыразимого иначе сценария.

<a id="4-missing-values"></a>

### 4. Пропуски

Сохранять `NaN`: scaler с NaN пишет NaN, не заменяет прогрев нулём и не удерживает старое.

<a id="5-invalid-fitted-parameters"></a>

### 5. Некорректные обученные параметры

Компиляция отклоняет неконечное среднее/масштаб и неположительный масштаб.
Ошибка идентифицирует определение и выходной ID.

<a id="6-numeric-representation"></a>

### 6. Числовое представление

Нужно одно межъязыковое представление параметров при выходных `f32`/`f64`.
Решить: JSON `f64` с приведением к `F` или фиксированное исполнение `f64`.
Текущий `Float` не умеет конверсию из `f64`, generic-пути нужна небольшая правка трейта.

<a id="7-ids-and-collisions"></a>

### 7. ID и конфликты

Каждый итоговый выход имеет явный стабильный ID. Компиляция отклоняет дубли и
неизвестные исходные ID. Решить, могут ли исходный/конечный ID совпадать: удобно
для identity, но должно быть однозначно в разных раскладках.

<a id="8-serialization-versioning"></a>

### 8. Версии сериализации

У `PipelineSpec` своя версия, не версия экстрактора. Строго отклонять неизвестные
поля/версии, один канонический порядок для идентичных артефактов Rust/Python.

<a id="proposed-implementation-sequence"></a>

## Предлагаемая последовательность

<a id="phase-1-record-the-contract"></a>

### Этап 1: зафиксировать контракт

- ADR по решениям выше.
- Канонический JSON с исходной спецификацией и группой стандартного масштабирования.
- Примеры identity, масштабирования, NaN прогрева и ошибок.

До согласования контракта не рефакторить конвейер.

<a id="phase-2-core-definitions-and-compiler"></a>

### Этап 2: определения и компилятор ядра

- Документированные `PipelineSpec` и определения преобразований.
- Разрешение входных ID, назначение выходных индексов при компиляции.
- Проверка размерностей, ID, параметров, ёмкости до состояния исполнения.
- Масштабирование в непрерывные массивы/boxed-срезы для обновлений без выделений.
- Тесты сериализации и отклонения под существующим `serde`.

<a id="phase-3-runtime-replacement"></a>

### Этап 3: замена исполнения

- Новый модуль вокруг экстрактора и скомпилированного этапа.
- Начальные итоговые ячейки NaN.
- Преобразования после принятого события, не после отклонённого.
- Доступ к исходным/итоговым значениям и итоговым ID.
- Удалить старый конвейер после покрытия нужного эквивалентного поведения.

<a id="phase-4-python-parity"></a>

### Этап 4: совпадение Python

- Та же спецификация и канонический JSON через Python.
- История пакетами и пособытийный Rust через одну семантику.
- Сохранить выходной dtype без изменения смысла параметров.
- Общие фикстуры с одинаковыми ID, порядком, NaN и числами.

<a id="phase-5-end-to-end-verification"></a>

### Этап 5: сквозная проверка

- Расширить исторический пример необязательной спецификацией входа модели либо
  добавить второй сфокусированный пример.
- Проверить одинаковые итоговые векторы сохранённого артефакта в Rust/Python.
- Форматирование, все цели/возможности workspace, Python, блокнот, строгий Clippy.

<a id="performance-constraints"></a>

## Ограничения производительности

- Разбор/компиляция могут выделять память.
- `handle_event` и преобразования — нет.
- ID разрешаются в индексы при компиляции, не на событии.
- Циклы используют готовое непрерывное хранилище, без trait objects до обоснования замерами.
- Итоговый вектор пишется напрямую, без временных векторов на событие.

<a id="acceptance-criteria"></a>

## Критерии приёмки

- Один канонический артефакт полностью описывает извлечение и преобразование модели.
- Rust/Python одинаково сериализуют/читают его.
- Стандартное масштабирование с параметрами каждого признака.
- Неизвестные входы, повторные выходы, неверные размерности/параметры отклоняются до событий.
- Прогрев/пропуски остаются NaN.
- Отклонённое событие сохраняет исходное/преобразованное состояние.
- Итоговые ID и порядок стабильны и проверены.
- События/преобразования не выделяют память в куче.
- Старый конвейер и ссылки на удалённые интерфейсы удалены.
- Тесты workspace/Python, блокнот, примеры, форматирование, строгий Clippy проходят.

<a id="non-goals"></a>

## Вне задачи

- Загрузка истории конкретной биржи.
- Метки и обучение моделей.
- Общий граф или произвольные пользовательские преобразования.
- Хранение бинарных ML-моделей внутри `fiml`.
- Признаки стакана: отдельное проектирование.

<a id="work-after-transformations"></a>

## После преобразований

Следующая независимая задача — признаки стакана: владение/синхронизация состояния,
маршруты и перевод `Decimal` в `Float` экстрактора.
