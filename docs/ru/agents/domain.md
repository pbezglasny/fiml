# Документация предметной области

Как инженерным навыкам использовать документацию предметной области при изучении репозитория.

<a id="before-exploring-read-these"></a>

## Перед изучением прочитайте

- **`CONTEXT.md`** в корне либо
- **`CONTEXT-MAP.md`** в корне, если существует: он указывает на `CONTEXT.md` каждого
  контекста. Прочитайте относящиеся к теме.
- **`docs/adr/`**: решения затрагиваемой области. В многоконтекстном репозитории
  также проверьте `src/<context>/docs/adr/`.

Если файлов нет, **продолжайте молча**. Не отмечайте отсутствие и не предлагайте
создать заранее. `/domain-modeling` (через `/grill-with-docs` и
`/improve-codebase-architecture`) создаёт их по мере разрешения терминов/решений.

<a id="file-structure"></a>

## Структура файлов

Один контекст (большинство репозиториев):

```text
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

Несколько контекстов (`CONTEXT-MAP.md` в корне):

```text
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← system-wide decisions
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← context-specific decisions
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

<a id="use-the-glossarys-vocabulary"></a>

## Используйте словарь

Называя понятие в задаче, предложении рефакторинга, гипотезе или тесте, используйте
термин из `CONTEXT.md`. Не переходите к синонимам, которых словарь явно избегает.

Если понятия нет, либо вы вводите чуждый проекту язык (пересмотрите), либо есть
реальный пробел (отметьте для `/domain-modeling`).

<a id="flag-adr-conflicts"></a>

## Отмечайте противоречия ADR

Если результат противоречит ADR, укажите это явно вместо молчаливой замены:

> _Противоречит ADR-0007 (заказы на основе событий), но стоит пересмотреть, потому что…_
