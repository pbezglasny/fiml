# Требования: генерация целей по временному горизонту для событийных торговых данных

<a id="1-goal"></a>

## 1. Цель

Реализовать генерацию целевых столбцов нерегулярных событийных рядов: сделок,
обновлений стакана, котировок, производных состояний рынка.

Для строки времени `t` система должна получать значение выбранного столбца в будущем:

`target_time = t + horizon`

Основное назначение — подготовка торговых наборов для обучения с учителем.

<a id="2-core-requirement"></a>

## 2. Основное требование

Для таблицы, отсортированной по времени событий:

  timestamp     mid_price   feature_1 ...
  ----------- ----------- ----------- -----
  t0                  ...         ... ...
  t1                  ...         ... ...

и горизонта вроде `500ms` сформировать будущий столбец состояния на `t + 500ms`.

Поток нерегулярен. Сдвиги строк вроде `shift(N)` НЕ ДОЛЖНЫ представлять временной горизонт.

<a id="3-lookup-semantics"></a>

## 3. Семантика поиска

<a id="31-state-at-time-semantics-----default"></a>

### 3.1 Состояние на момент времени — по умолчанию

Для значений состояния:

- средняя цена;
- лучшая покупка;
- лучшая продажа;
- спред;
- дисбаланс стакана;
- микропрайс;
- волатильность/индикаторы состояния

по умолчанию ОБЯЗАТЕЛЬНО возвращать последнее известное значение не позже `target_time`.

Для исходного `t` и горизонта `H`:

`T = t + H`

выбрать время события:

`t* = max(t_i) such that t_i <= T`

и значение нужного столбца в `t*`.

Это соответствует pandas `merge_asof(..., direction="backward")`.

Пример:

``` text
0.400  mid_price=100
0.490  mid_price=101
0.700  mid_price=102

source time: 0.000
horizon:     0.500
target time: 0.500

result: 101
```

Значение `101`: именно такое состояние известно на `0.500`.

<a id="32-first-event-after-semantics-----optional"></a>

### 3.2 Первое событие после момента — необязательно

СЛЕДУЕТ также поддержать первое событие в `target_time` или позже:

`t* = min(t_i) such that t_i >= T`

Это pandas `merge_asof(..., direction="forward")`.

Режим означает «первое наблюдаемое обновление после горизонта», не точное состояние
на горизонте. API ОБЯЗАН явно различать эти интерпретации, не смешивая молча.

<a id="4-required-inputs"></a>

## 4. Обязательные входы

Операция ОБЯЗАНА поддерживать:

- входной DataFrame/таблицу;
- столбец времени;
- исходный столбец значений;
- временной горизонт;
- направление/семантику поиска.

Концептуальный API:

``` python
future_value(
    df,
    timestamp_column="timestamp",
    value_column="mid_price",
    horizon="500ms",
    direction="backward",
)
```

Имена могут отличаться, если другой API лучше вписывается в проект.

<a id="5-required-outputs"></a>

## 5. Обязательные выходы

Для каждой исходной строки СЛЕДУЕТ уметь показать:

- исходное время `t`;
- вычисленное `target_time = t + horizon`;
- время найденного события;
- найденное будущее значение/состояние.

Основной результат может быть только Series/столбцом целей, но сохранять время
совпадения внутри настоятельно рекомендуется для проверки и отладки.

Пример:

| timestamp | mid_price | target_time | matched_timestamp | target_mid_price |
| --- | ---: | --- | --- | ---: |
| 00.017 | 100.02 | 00.517 | 00.510 | 100.11 |

<a id="6-derived-targets"></a>

## 6. Производные цели

Из будущего значения ДОЛЖНО быть просто получать ML-цели.

<a id="61-absolute-change"></a>

### 6.1 Абсолютное изменение

`future_value - current_value`

<a id="62-simple-return"></a>

### 6.2 Простая доходность

`future_value / current_value - 1`

Пример:

``` python
target_return = future_mid_price / mid_price - 1
```

<a id="63-log-return"></a>

### 6.3 Логарифмическая доходность

`log(future_value / current_value)`

Пример:

``` python
target_log_return = np.log(future_mid_price / mid_price)
```

<a id="64-classification-target"></a>

### 6.4 Классификационная цель

Поддержать метки направления с настраиваемыми порогами.

Пример с `epsilon`:

``` text
return > +epsilon  ->  1   (up)
return < -epsilon  -> -1   (down)
otherwise          ->  0   (neutral)
```

Политику порога СЛЕДУЕТ отделить от временного поиска.

<a id="7-separation-between-features-and-targets"></a>

## 7. Разделение признаков и целей

Вычисления признаков и целей ОБЯЗАНЫ быть логически раздельны.
Признаки строки `t` ОБЯЗАНЫ зависеть только от информации не позже `t`.
Цели МОГУТ использовать информацию после `t`.

Концептуально:

``` text
past / present                       future

------ features ------|------ target lookup ------>
                      t               t + H
```

Генерация целей НЕ ДОЛЖНА менять признаки будущей информацией.
Разделение нужно для снижения риска заглядывания вперёд/утечки.

<a id="8-multiple-horizons"></a>

## 8. Несколько горизонтов

СЛЕДУЕТ разрешить несколько горизонтов без дублирования основной логики.

Пример:

``` text
target_return_100ms
target_return_500ms
target_return_1s
target_return_5s
```

Возможный API:

``` python
build_targets(
    df,
    value_column="mid_price",
    horizons=["100ms", "500ms", "1s"],
)
```

Именно этот API не обязателен, если противоречит архитектуре.

<a id="9-sorting-and-timestamp-requirements"></a>

## 9. Сортировка и время

Реализация ОБЯЗАНА правильно обрабатывать порядок времени.

1. Проверять/обеспечивать возрастание до as-of поиска.
2. Сохранять соответствие целей исходным строкам.
3. Поддерживать высокую точность торгового времени.
4. Не понижать разрешение с потерей информации.
5. Явно определять повторные метки.

Для повторов СЛЕДУЕТ использовать и документировать детерминированную семантику.

<a id="10-missing-future-data"></a>

## 10. Недостающие будущие данные

В конце набора может не хватать будущих данных на нужный горизонт.

Пример:

``` text
dataset ends: 10:00:10
row time:     10:00:09.8
horizon:      500ms
target time:  10:00:10.3
```

НЕЛЬЗЯ молча использовать неподходящее прошлое значение так, будто будущий горизонт
наблюдаем за границей набора. Такие строки СЛЕДУЕТ помечать пропуском (`NaN`/null)
или явно некорректными.

Особенно для backward нужно различать «состояние на доступное целевое время»
и «цель за пределами наблюдаемого интервала».

<a id="11-optional-maximum-match-distance"></a>

## 11. Необязательное максимальное расстояние

API СЛЕДУЕТ поддерживать необязательный допуск/максимальную дистанцию.

Пример:

``` python
future_value(
    ...,
    horizon="500ms",
    tolerance="100ms",
)
```

В forward слишком далёкое первое событие после цели даёт пропуск.
В backward допуск позволяет отклонять устаревшее состояние.

<a id="12-data-leakage-requirements"></a>

## 12. Требования против утечки

Реализация ОБЯЗАНА учитывать построение ML-наборов. Тесты ОБЯЗАНЫ проверять:

- признаки не обращаются к времени после своей строки;
- цели используют настроенный будущий горизонт;
- целевые столбцы случайно не попадают во входы признаков;
- сортировка/соединение не переносит цель на неверную исходную строку.

Построитель целей не обязан владеть всей политикой утечек конвейера, но безопасное
использование должно быть простым.

<a id="13-performance"></a>

## 13. Производительность

Ожидается работа с большими событийными наборами:

- без построчных циклов Python;
- векторные, индексные или as-of операции;
- примерно `O(N)` или `O(N log N)` по реализации;
- без лишних копий всего DataFrame;
- миллионы событий.

Для первой Python/pandas-реализации допустим эталон `pandas.merge_asof`.

<a id="14-reference-behavior-in-pandas"></a>

## 14. Эталонное поведение pandas

Приближённое выражение состояния на горизонте:

``` python
horizon = pd.Timedelta("500ms")

left = df[["timestamp"]].copy()
left["target_time"] = left["timestamp"] + horizon

right = (
    df[["timestamp", "mid_price"]]
    .rename(columns={
        "timestamp": "matched_timestamp",
        "mid_price": "future_mid_price",
    })
)

result = pd.merge_asof(
    left.sort_values("target_time"),
    right.sort_values("matched_timestamp"),
    left_on="target_time",
    right_on="matched_timestamp",
    direction="backward",
)
```

Производственная реализация не обязана точно копировать этот код.

<a id="15-example"></a>

## 15. Пример

Вход:

``` text
timestamp   mid_price
0.000       100.0
0.200       100.1
0.490       100.2
0.700       100.4
1.100       100.3
```

Для:

``` text
horizon = 500ms
direction = backward
```

Ожидается:

``` text
source t=0.000
target_time=0.500
matched_timestamp=0.490
future_mid_price=100.2
```

Для:

``` text
source t=0.200
target_time=0.700
```

ОБЯЗАТЕЛЬНО выбрать точное событие в `0.700`:

``` text
future_mid_price=100.4
```

<a id="16-tests"></a>

## 16. Тесты

Минимум проверить:

1. Точное совпадение `t + horizon`.
2. Нет точного совпадения: backward выбирает последнее до цели.
3. Forward выбирает первое после цели.
4. Нерегулярные интервалы.
5. Несколько событий внутри горизонта.
6. Нет наблюдаемых данных на горизонте.
7. Повторные метки.
8. Неотсортированный вход.
9. Нулевой горизонт.
10. Несколько горизонтов.
11. Доходность.
12. Логарифмическую доходность.
13. Трёхклассовую цель.
14. Необязательный допуск.
15. Сохранение соответствия исходным строкам.

<a id="17-acceptance-criteria"></a>

## 17. Критерии приёмки

Реализация завершена, когда:

- цели основаны на прошедшем времени, не числе строк;
- нерегулярные потоки обработаны правильно;
- backward/состояние поддержан и принят по умолчанию для рыночных состояний;
- forward/первое событие доступен явно;
- недоступные горизонты дают пропуск/некорректную цель;
- время совпадения можно проверить;
- доходности/классы просто строятся поверх будущего значения;
- реализация векторная, подходит большим торговым наборам;
- автоматические тесты покрывают перечисленные края;
- признаки/цели разделены против утечки будущего.

<a id="18-design-principle"></a>

## 18. Принцип проектирования

Примитив должен оставаться небольшим:

> Для строки времени `t`, горизонта `H` и исходного столбца получить корректно
> определённое значение, соответствующее `t + H`.

Доходность, логарифмическую доходность, классификацию и несколько горизонтов
стройте поверх примитива, не встраивая всю семантику в большую функцию.
