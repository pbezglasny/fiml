<a id="scalar-definition-migration-rust"></a>

## Миграция скалярных определений (Rust)

`TransformerDefinition` хранит публичные ID `input`, `output` и публичный enum
`TransformerOperation` только с параметрами расчёта. Конструкторы вроде
`TransformerDefinition::lagged(input, output, 2)` прежние. Прямое создание
`TransformerDefinition::Lagged { input, output, lag_window: 2 }` замените на:

```rust
use fiml::{FeatureId, TransformerDefinition, TransformerOperation};

let definition = TransformerDefinition {
    input: FeatureId::new("price"),
    output: FeatureId::new("previous_price"),
    operation: TransformerOperation::Lagged { lag_window: 2 },
};

if let TransformerOperation::Lagged { lag_window } = &definition.operation {
    println!("{}: {} events ago", definition.input.as_str(), lag_window);
}
```

Читайте ID из структуры, разбирайте параметры через `definition.operation`.
`TransformerOperation::Identity` не имеет полей. Создание конвейера по-прежнему
проверяет ID и параметры. Поведение операций сохраняется. Версия `4.0` использует
оболочку графа; старые артефакты нужно пересоздать и экспортировать.

<a id="rolling-scalar-statistics"></a>

## Скользящая скалярная статистика

`TransformerDefinition::rolling_std`, `rolling_min`, `rolling_max`, `rolling_range`
читают любой скаляр предыдущего этапа, включая обученные векторные выходы.
Конструкторы по отсчётам принимают `(input, output, window, warmup_policy)`;
`window` — положительное число наблюдений без лимита лага 10 000. Для среднего
используйте `sma`. Стандартное отклонение — генеральное (`ddof=0`); одно наблюдение
даёт нулевые std и range.

Варианты `_timed` принимают окно `Duration` с агрегацией по умолчанию 1 мс.
`_timed_with_aggregation` принимает `(input, output, window, aggregation, warmup_policy)`.
Длительности — положительные целые миллисекунды, окна кратны агрегации. Каждое
конечное наблюдение учитывается, включая повторные метки/значения. Привязанные к
эпохе интервалы истекают при `bucket_start + window <= source_clock`.
Грубая агрегация удаляет интервалы целиком, не отбрасывая пики внутри них.
Это семантика временной волатильности, а не выбор последнего наблюдения временных лагов.

В историю входят только наблюдаемые конечные входы. Наблюдаемый NaN/бесконечность
выдаёт NaN до следующего конечного наблюдения, сохраняя историю. Ненаблюдаемые входы
сохраняют выход, кроме продвижения часов источника: оно обновляет истечение и
помечает временной выход наблюдаемым. Замена контекста не продвигает/обновляет
статистику; чистый контекст не имеет часов. Составные часы следуют правилам
векторных этапов; каждое конечное наблюдение с этой меткой учитывается.
Пустые окна и неконечная арифметика дают NaN. Очень большие конечные входы могут
переполнить дисперсию; соответствующие сводки перестают влиять после истечения.

`FirstValue` сразу открывает непустое окно. `FullWindow` ждёт заданное число
конечных наблюдений либо полную длительность от первого конечного наблюдения.
Готовность сохраняется через разрывы, но пустое временное окно всё равно даёт NaN.

Все статистики и политики одного входа разделяют кольцевую историю в этапе;
временные группы также разделяют агрегацию. Различное окно запрашивается один раз.
Заранее выделенное дерево сводок объединяет смещённые моменты и точные min/max
без вычитательных обновлений дисперсии и выделений на событиях. Стоимость обновления
и запроса — `O(log slots)`. На 64-битной платформе дерево занимает
`96 * next_power_of_two(slots)` байт плюс `8 * slots` для ID временных интервалов.
Число слотов по отсчётам равно максимальному окну; по времени —
`max_window / aggregation + 2`, максимум 1 000 000 (около 104 МиБ с деревом).
Для длинных окон уменьшайте память более грубой агрегацией.

JSON `4.0` добавляет `rolling_std`, `rolling_min`, `rolling_max`, `rolling_range`
и варианты `_timed`. Обязательны `input`, `output`, `window`, `warmup_policy`;
временные окна — строки длительности с необязательной `aggregation` (по умолчанию
`"1ms"`, при стандартном значении не записывается). Старые артефакты ведут себя
прежним образом; старые среды не читают новые типы. См. [схему](../pipeline-spec.schema.json)
и [пример состояния рынка на разных масштабах](../../crates/fiml/examples/transformers.rs).

<a id="rolling-trajectory-shape"></a>

## Форма скользящей траектории

`rolling_slope`, `rolling_path_length`, `rolling_positive_movement`,
`rolling_negative_movement`, `rolling_direction_change_count`, `rolling_max_drawdown`
имеют ту же сигнатуру окон по отсчётам. Читают любой скаляр предыдущего этапа,
включая преобразования и обученные компоненты. Окно — положительное число
наблюдений; временных вариантов нет.

Для `x[0..n]` наклон — обычная регрессия наименьших квадратов по индексам `0..n-1`,
в единицах входа на наблюдение. Длина пути суммирует `abs(dx)`, положительное
движение — `max(dx, 0)`, отрицательное — `max(-dx, 0)`. Длина равна сумме движений,
разность последнего/первого — их разности. Развороты считаются после исключения
нулевых дельт: `+, 0, -` — один разворот. Учитываются только дельты с обоими концами
в окне. Максимальная просадка — `max(0, max(x[i] - x[j]))` при `i < j` в абсолютных
единицах, не процентах; работает с нулевыми и отрицательными входами.

| Окно | Наклон | Длина пути | Положительное | Отрицательное | Развороты | Просадка |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `[1, 2, 3, 4]` | 1 | 3 | 3 | 0 | 0 | 0 |
| `[1, 4, 1, 4]` | 0.6 | 9 | 6 | 3 | 2 | 3 |
| `[1, 3, 3, 1]` | 0 | 4 | 2 | 2 | 1 | 2 |

Первые две траектории имеют одинаковые концы и средние, но разную форму.
`FullWindow` ждёт `window` конечных наблюдений; `FirstValue` открывает частичные
окна. Наклону всегда нужно минимум два, поэтому при `window=1` он всегда NaN.
Остальные измерения одного отсчёта — ноль. NaN/бесконечность выдаёт NaN без записи
в историю; следующий конечный вход соединяется с предыдущим сохранённым.
Ненаблюдаемые входы сохраняют выход. Неконечная арифметика даёт NaN и восстанавливается
после ухода затронутых отсчётов из окна.

Все шесть видов разделяют одно дерево траектории на вход/этап для окон и политик,
отдельное от меньшего дерева статистики. Окно запрашивается один раз. Обновления/
запросы — `O(log max_window)` без выделений. На 64 битах память —
`192 * next_power_of_two(max_window)` байт (около 24 МиБ на 100 000 отсчётов).
Моменты регрессии используют наблюдаемое начало для сохранения малых изменений
больших значений. Слияния сохраняют хронологию при циклическом переходе буфера.

JSON `4.0` использует шесть имён как `type` с обязательными `input`, `output`,
`window`, `warmup_policy`. Старые артефакты прежние; старые среды не читают новые типы.

<a id="experimental-rolling-path-signatures"></a>

## Экспериментальные скользящие сигнатуры пути

`FittedStage::rolling_path_signature(input, output_prefix, window, warmup_policy)`
читает один скаляр и заменяет раскладку шестью координатами. В Python передайте
числовой словарь в `spec.add(parent, stage)` с `type="rolling_path_signature"`,
`input`, `outputs`, `window`, `warmup_policy`. Шесть ID задаются в порядке ниже.
Обучение и новые зависимости не нужны. Следующие этапы выбирают/масштабируют координаты.

Для сохранённых конечных `x[0..n]` соедините `(i/(n-1), x[i])` прямыми. Время —
**индекс наблюдения**, независимо от меток, в диапазоне `[0, 1]` при `n >= 2`,
включая неполные окна. Значения сохраняют единицы. Начальная позиция не важна:
сигнатуры описывают приращения. Для одного отсчёта все шесть координат нулевые.

| Порядок | Стандартный суффикс ID | Определение |
| --- | --- | --- |
| 1 | `__t` | Полное приращение времени (1 при двух и более наблюдениях) |
| 2 | `__x` | `x[last] - x[first]` |
| 3 | `__tt` | Половина квадрата приращения времени (0.5 при двух и более) |
| 4 | `__tx` | Интеграл `(t - t[start]) dx` |
| 5 | `__xt` | Интеграл `(x - x[start]) dt` |
| 6 | `__xx` | Половина квадрата приращения значения |

Нулевой уровень (константа 1) опущен. В `ij` канал `i` интегрируется перед `j`.
Для `[0, 1, 3]` выходы `[1, 3, 0.5, 1.75, 1.25, 4.5]`; для перестановки приращений
`[0, 2, 3]` — `[1, 3, 0.5, 1.25, 1.75, 4.5]`. Одни концы не различают эти пути.
Уровень 2 всё же теряет информацию: при фиксированных числе наблюдений и концах
перестановка внутренних значений не меняет координаты.

`window` — положительное число наблюдений с концами. `FullWindow` (по умолчанию
Python) выдаёт NaN до нужного числа конечных наблюдений; `FirstValue` — частичное
окно. В историю входят только наблюдаемые конечные входы. NaN/бесконечность даёт
шесть NaN, сохраняя историю и не занимая шаг. Следующее конечное соединяется с
предыдущим. Ненаблюдаемые события сохраняют выход и помечают его ненаблюдаемым.
Контекст не продвигает историю/выходы. Все координаты наследуют часы выбранного
входа. Неконечная арифметика даёт NaN покоординатно и восстанавливается после вытеснения.

Реализация компонует уровни тензора по
`S1(AB) = S1(A) + S1(B)` и
`S2(AB) = S2(A) + S1(A) tensor S1(B) + S2(B)`
([тождество Чэня](https://arxiv.org/abs/1603.03788)). Узел дерева описывает диапазон
наблюдений; слияние включает соединяющий отрезок. Кольцевое дерево даёт
`O(log window)` без полного пересчёта и вычитания накопленных сигнатур при вытеснении.
Время нормализуется только при записи выхода. Формулы по концам для `x`, `xx`
избегают потери точности при возврате большого отклонения к началу. Создание
резервирует `2 * next_power_of_two(window)` сводок по 72 байта на 64 битах
(около 18 МиБ на 100 000 наблюдений); каждый этап владеет историей.
Прогрев, обновления и вытеснение не выделяют память в куче.

JSON `4.0` добавляет `rolling_path_signature` с `input`, `outputs`, `window`,
`warmup_policy`. `outputs` содержит ровно шесть уникальных незарезервированных ID
в указанном порядке. Старые артефакты прежние; старые среды отклоняют тип.
История не сериализуется: загрузка начинает новое воспроизведение.

Rust/Python воспроизводят `tests/fixtures/rolling_path_signature.json`, включая
вытеснение, чужие символы и промежуточные пропуски. Независимые тесты Python
интегрируют прямые отрезки без дерева/композиции Чэня. Проверки используют
`abs(actual - expected) <= 1e-12 + 1e-12 * abs(expected)` с совпадающими NaN.
Это допуск фикстур, не гарантия ошибки для произвольных величин.
Criterion: `cargo bench -p fiml --bench path_signature`.

## Серии и давность состояния

Преобразования классифицируют скаляр предыдущего этапа. После `delta`,
`simple_return`, `log_return` они измеряют устойчивость изменений; можно применять
напрямую к знаковым признакам, например дисбалансу стакана. `nonzero` — сигнал
вне нейтрального интервала, а не сравнение соседних значений.

| Операция | Выход |
| --- | --- |
| `positive_streak` | Последовательные конечные наблюдения больше epsilon |
| `negative_streak` | Последовательные конечные наблюдения меньше минус epsilon |
| `observations_since_positive` | Конечные наблюдения с последнего положительного сигнала |
| `observations_since_negative` | Конечные наблюдения с последнего отрицательного сигнала |
| `observations_since_nonzero` | Конечные наблюдения с последнего сигнала любого знака |
| `time_since_positive` | Миллисекунды с последнего положительного сигнала |
| `time_since_negative` | Миллисекунды с последнего отрицательного сигнала |
| `time_since_nonzero` | Миллисекунды с последнего сигнала любого знака |

Rust принимает `(input, output, epsilon)`, методы `ScalarStage` Python —
`(input, *, epsilon=0.0, output=None)`. Epsilon конечен и неотрицателен. Обе границы
`[-epsilon, epsilon]` нейтральны, включая знаковый ноль. Нейтральное наблюдение
сбрасывает обе серии и продвигает начатую давность в наблюдениях. Совпадение
увеличивает свою серию на один и обнуляет давность. Все выходы начинаются с NaN;
первое конечное наблюдение даёт серии 0/1. Давность остаётся NaN до первого совпадения.

Пример с нулевым epsilon:

| Время (мс) | Сигнал | Положительная серия | Наблюдений после положительного | Время после положительного (мс) |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 1 | 1 | 0 | 0 |
| 10 | 2 | 2 | 0 | 0 |
| 20 | 0 | 0 | 1 | 10 |
| 40 | -1 | 0 | 2 | 30 |
| 70 | -2 | 0 | 3 | 60 |

Наблюдаемый NaN/бесконечность сохраняет счётчики и метки совпадений, выдавая NaN
до конечного входа. Пропуски не прерывают серию и не увеличивают давность по
наблюдениям. Без наблюдений счётчики сохраняются. Они насыщаются на `2^53`
(9 007 199 254 740 992), максимальном последовательном целом в `f64`, и нормально
сбрасываются на совпадении/нейтральном сигнале. Разности времени считаются в
расширенном типе для всего `i64`, затем приводятся к `f64`; свыше `2^53` мс возможно округление.

Временная давность использует часы источника и обновляется при их продвижении
даже без нового скаляра. Такое обновление наблюдаемо дальше, но не создаёт нового
совпадения в текущем этапе. Для одного символа часы продвигают его принятые события,
не другие символы и не глобальные тики. Составные входы наследуют максимальные
часы, включая наблюдения с более старой меткой. Повторы одной метки считаются
отдельно; совпадение обнуляет давность. Наблюдаемый пропуск скрывает временной
выход до конечного входа, но прошедшее время включает пропуск. Замена контекста
не продвигает состояние; чистый контекст не имеет наблюдений/часов.

Выход использует состояние постоянного размера без истории и выделений при
обновлении. JSON `4.0` использует указанные имена `type` и обязательные `input`,
`output`, `epsilon`. Старые артефакты прежние; старые среды не загружают новые операции.

<a id="current-interface"></a>

## Текущий интерфейс

Для новых конвейеров используйте [API графа](multiple_output.md). `PipelineSpec`
владеет расширяемым добавлением графом с корнем-экстрактором. Добавляйте скалярный
или обученный векторный этап под явным родителем, регистрируйте именованные выходы
и создавайте независимый экземпляр. Общие узлы исполняются раз на принятое событие.

Rust читает `pipeline.output(name).unwrap().values()` либо разрешает сохранённый
`OutputId` через `output_by_id`. Python получает независимый снимок через
`pipeline.output(name).values()`. Пакеты Python возвращают словари всех выходов,
DataFrame-воспроизведение — словарь таблиц. Выходы корня и рёбра преобразований
содержат только активные координаты; исходная диагностика может содержать резерв.

JSON графа — конвейер `4.0`, вложенный экстрактор `2.0`. См.
[схему](../pipeline-spec.schema.json) и
[полный пример](multiple_output-arc.md#artifact-format-and-compatibility).
Среда владеет буферами/состоянием; живая история не сериализуется.

<a id="historical-interface-hardening-notes"></a>

## Исторические заметки об укреплении интерфейса

<a id="p3-transformation-validation-diagnostics"></a>

### P3: Диагностика проверки преобразований

Статус: частично

Приоритет: средний

Ошибка содержит индекс и типизированную причину, но не ошибочные входной/выходной
ID, что усложняет диагностику больших артефактов.

Критерии завершения:

- Включить индекс, входной и выходной ID в ошибку.
- Сохранить типизированные ошибки исполнения без выделений; при создании они допустимы.
- Проверить одинаковый контекст загрузки JSON в Rust/Python.

<a id="p4-end-to-end-failure-and-warm-up-examples"></a>

### P4: Сквозные примеры ошибок и прогрева

Статус: частично

Приоритет: средний

Пример Python показывает успешную загрузку JSON и масштабирование. Пользовательские
примеры пока не показывают NaN прогрева и ошибки проверки/отклонения событий.

Критерии завершения:

- Добавить/расширить пример воспроизведения входа модели Rust.
- Показать NaN прогрева, успешное масштабирование и атомарность отклонения.
- Использовать тот же канонический артефакт, что в проверке совпадения.

Снимки конфигурации и независимые сборки теперь входят в контракт графа.
Текущее поведение см. в [multiple_output.md](multiple_output.md).

## Отложенная работа

Не добавляйте общие графы преобразований, сериализацию рабочего состояния и
предположительные экспортёры. Новый экспортёр нужен только для конкретной

## Контекст вызывающего кода

`FeatureKey::Context { symbol, name }` регистрирует именованный предвычисленный
скаляр с обычными ID `FeatureDefinition` и слотами. `Symbol::GLOBAL` задаёт общую
область. У контекста нет подписок на события и калькулятора индикатора.

```rust,ignore
let key = FeatureKey::Context {
    symbol: Symbol::GLOBAL,
    name: "previous_day_high".to_owned(),
};
let definition = FeatureDefinition::new(key, FeatureId::new("previous_day_high"));
// Include definition in the extractor spec before constructing the pipeline.
pipeline.update_context(&[("previous_day_high", Some(105.0))])?;
pipeline.update_context(&[("previous_day_high", None)])?; // clear to NaN
```

`FeatureExtractor::update_context` и `Pipeline::update_context` проверяют все ID/
значения до записи. ID должны быть контекстными и не повторяться. Числа конечны.
Пропущенные значения сохраняются; пустое обновление ничего не делает. Обновления
и пересчёт конвейера не выделяют память после создания. `validate_context`
проверяет то же без изменения для подготовки пакета.

Обновление контекста выполняет этапы без состояния во всём конвейере, а этапы
с состоянием выдают сохранённые выходы. Не меняются время, календарь, стаканы,
истории индикаторов и лагов. Контекст не устанавливает флаги наблюдения: SMA/EMA
и преобразования изменений не считывают замены. Лаги событий могут считывать
удерживаемый контекст при следующих принятых событиях.

Добавленный вид JSON сохраняет версии экстрактора `2.0` и конвейера `4.0`:

```json
{
  "kind": "context",
  "source": {"type": "context"},
  "options": {"name": "previous_day_high"},
  "outputs": [{"id": "previous_day_high"}]
}
```

Поместите индикатор в группу символа. Без `outputs` используется стандартный ID,
кодирующий длины/содержимое символа и имени контекста. Имя непустое. Контекст не
добавляет `required_events`. Артефакты хранят определения, не значения; создание
инициализирует NaN. См. [примеры Python](crates/fiml-python/README.md#externally-supplied-context)
для расписаний обучения и DataFrame частями. Вызывающий код подаёт доступные
значения и отвечает за очистку устаревших и границы сессий.
